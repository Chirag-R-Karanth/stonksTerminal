# PERSONAL FINANCIAL TERMINAL — MASTER BUILD PROMPT

## 0. ROLE

You are building a **private, single-user Bloomberg-style financial terminal** for personal research and portfolio analysis.

This is **NOT a SaaS product**.

This is **NOT a website**.

This is **NOT a Bloomberg clone intended for public release**.

This is a personal desktop financial workstation inspired by the interaction model, information density, keyboard-first workflow, command system, and analytical capabilities of Bloomberg Terminal.

The goal is:

> Build a serious personal financial research terminal that lets one user investigate markets, securities, macroeconomics, financial statements, news, portfolios, valuation, risk, and eventually quantitative strategies from one application.

The application should feel like a **professional terminal**, not a consumer finance dashboard.

---

# 1. CORE PRODUCT PHILOSOPHY

The application must prioritize:

1. Data integrity
2. Security
3. Reliability
4. Speed
5. Keyboard-first interaction
6. Information density
7. Local-first operation
8. Extensibility
9. Maintainability
10. Analytical usefulness

Do NOT optimize for:

- flashy marketing pages
- SaaS architecture
- multi-user support
- authentication systems for other users
- billing
- social features
- unnecessary cloud infrastructure
- mobile applications
- AI before the core system works
- excessive animations
- generic dashboard aesthetics

The application is for **one user**.

Do not build infrastructure that only exists because a commercial SaaS product would need it.

---

# 2. WHAT THIS SHOULD FEEL LIKE

The application should feel like a professional financial terminal.

It should be:

- dense
- dark
- highly readable
- information-rich
- keyboard-driven
- fast
- structured
- utilitarian
- precise

It should NOT feel like:

- Robinhood
- a banking app
- a generic React dashboard

- a crypto trading landing page

Think:

> Bloomberg Terminal + modern Linux terminal + quantitative research workstation.

The interface should contain information without becoming visually chaotic.

```text

    ↓
Command / Interaction Layer
    ↓
Application Services
    ↓

    ↓

    ↓

    ↓

```

Potential technology choices:

### UI

Prefer:

- GTK
- Qt
- or another proper native desktop GUI toolkit

Do NOT default to a web application simply because it is easier.

### Backend / analytical engine

Python is acceptable and preferred for:

- financial calculations

- quantitative research
- data ingestion

Use:

- NumPy

- PyArrow
- Parquet

Use additional libraries only when justified.

If required later, use:

```text

```

or another appropriate compiled language.

Do NOT prematurely rewrite everything in Rust.

## DuckDB

Use for:

- factor calculations

## Parquet

Use for:

# 8. DATA PROVIDER ARCHITECTURE

The application must NEVER hard-code itself around one data provider.

Create an abstraction:

```text
MarketDataProvider
FundamentalDataProvider
NewsProvider
MacroDataProvider
CorporateActionsProvider
```

Then implement provider adapters.

Example:

```text
providers/
    market/
        provider_base.py
        provider_a.py
        provider_b.py

    fundamentals/
        provider_base.py
        sec.py
        provider_a.py

    news/
        provider_base.py
        provider_a.py

    macro/
        provider_base.py
        fred.py
        rbi.py
```

The application should be able to replace a provider without rewriting the UI or analytics engine.

# 10. SECURITY

Security is extremely important.

The application may eventually contain:

- API keys
- broker credentials
- portfolio information
- private research
- transaction history

Therefore:

## API keys

Never expose API keys to the UI.

BAD:

```text
UI → external API
```

GOOD:

```text
UI
 ↓
Local backend
 ↓
Secure credential store
 ↓
External API
```

Use:

- environment variables during development
- OS credential/keyring facilities where appropriate
- encrypted storage where necessary

Never commit secrets.

Never place secrets in source code.

Never place API keys in frontend JavaScript.

Never log secrets.

Never print access tokens.

# 17. SECURITY / DATA INTEGRITY PRINCIPLE

The application must NEVER casually overwrite user data.

For all persistent data:

- validate input
- use transactions
- make backups where appropriate
- use atomic writes
- handle corruption
- handle failed imports
- preserve previous versions when practical

If a migration is required:

```text
backup
 ↓
validate
 ↓
migrate
 ↓
verify
 ↓
commit
```

Never:

```text
delete old database
 ↓
create new database
```

without a backup.

# 50. FINAL PRINCIPLE

Do not build a pretty financial dashboard.

Build a **financial instrument**.

The application should eventually become the place where the user can:

```text
LOOK
SEARCH
ANALYZE
COMPARE
MODEL
TRACK
RESEARCH
BACKTEST
DECIDE
```

from one keyboard-driven desktop environment.

The goal is not to reproduce every Bloomberg feature.

The goal is to reproduce the **concept**:

> One extremely powerful workstation through which the user can access, analyze, and act upon financial information.

Build it incrementally.

Keep the architecture clean.

Keep data ownership local.

Keep credentials secure.

Never fabricate financial data.

Never sacrifice data integrity for speed of implementation.

Do not add features merely because they sound impressive.

Every feature must make the terminal more useful as a serious personal financial research workstation.
